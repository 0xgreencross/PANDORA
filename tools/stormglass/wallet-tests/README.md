    NODE_PATH=/home/claude/node_modules PORT=8941 OUT=dir node tools/stormglass/wallet-tests/selftest.js  # the harness self-tests (about 6 minutes)

    PORT=8952 SCRIPT=../staging/staging.test.js RELEASE=1 LABEL=staging-release bash tools/stormglass/wallet-tests/run.sh   # staging release: every id of ../staging/manifest.json
    NODE_PATH=/home/claude/node_modules PORT=8905 OUT=dir node tools/stormglass/wallet-tests/selftest-staging.js         # the staging runner self-tests (about 4 minutes; OLD=1: against 50ac8a5's runner)

The full run takes about ten minutes: start it in the background (`(setsid nohup timeout 1800 bash run.sh > log 2>&1 &)`) and poll the log. A log without a final `XDONE rc=N` line means run.sh itself was killed: a failure.

## One runner for both suites (audit 5b)
`runner.js` is the only implementation of execution and persistence. `wallet.test.js` (production, `manifest.json`) and `../staging/staging.test.js` (staging, `../staging/manifest.json`, group `@staging`) each call `begin(module,…)` as their first step and `run(spec)` once their cases are registered; the spec gives the cases, the manifest, the target and the browser hooks. Everything below (release manifest checks, results schema, persistence, watchdogs, exit statuses) applies to both suites in the same words. The staging suite gained, by sharing it: a committed release manifest (RELEASE=1 refuses a missing, duplicate, unexpected or malformed id, a malformed manifest, CASES and preloads), run identity and schema-2 results, the earlier file moved aside before anything can fail, a snapshot before the first case and after every case, sticky persistence failures, case / cleanup / whole-run watchdogs, browser launch failure and loss, Node unhandled rejections, and SIGINT / SIGTERM results; its Chromium now also runs with `--webrtc-ip-handling-policy=disable_non_proxied_udp`. A malformed or duplicate staging id is collected at registration (exit 2 with a results file) instead of exiting before any results file exists. `node ../staging/staging.test.js --print-manifest` prints the staging registration.

Staging results additionally carry `staging`: `page` (the file under the repo root that was served), `stamp` (the build stamp read from the page), `candidate` (`rev`, full `commit`, `sha256` from the stamp, `gitSha256` = sha256 of `git show <commit>:index.html`, `matchesStamp`), `index` (this repo's index.html: sha256, `matchesStamp`, its commit). `target` is the staging page (full sha256, `source.commit` / `matchesHead`: the page's bytes equal HEAD's copy), and since the page is served from disk it is hashed again at the end (`target.sha256AtEnd`; a change is a harness failure). `harness` names both folders (`trees`, `dirty`, and the sha256 of every loaded file of tools/stormglass/staging and wallet-tests).

The staging suite's default `CASE_TIMEOUT_MS` is 480000 (st25 alone takes about two minutes on a quiet machine and more than four under load); the production default stays 120000. Cleanup deadline (audit 5b): each context a case opened gets 10 s to close and the whole cleanup of a case `CLEANUP_TIMEOUT_MS` (default 30000). A context that does not close, or a cleanup past the deadline, fails the case (`contextsDidNotClose`, `cleanupTimedOut`, listed in `cleanupTimedOut`) and is a harness failure; the browser must then still answer or it is killed and the run ends `incomplete`. A browser that does not close within 10 s at the end is killed and recorded as a harness failure. `status` may also be `aborted`: the process exited by some other path than the runner (recorded, never a success).

## Consumers: verify-results.js (audit 5b)
A results file is evidence only after `verify-results.js` accepts it: `node verify-results.js <results.json> --manifest <manifest.json> --expect-run <runId> --expect-sha <sha256 of the target> [--expect-candidate <sha256 of the candidate index.html> (staging)] [--cases a,b (a subset run of exactly these)] [--allow-uncommitted]`. It exits 1, listing every reason, for: the old bare array, another run id, status other than passed, not completed, exit other than 0, interrupted, any harness or persistence failure, another target sha256 (or a staging page that changed during the run), a manifest whose bytes differ from the one the run compared with or a registration that did not match it, a mode other than release (subset with `--cases`), selected / executed / passed ids that are not exactly the expected ones, duplicates, any failed, unexecuted, timed-out or cleanup-timed-out case, a staging build stamp whose candidate is not what git holds (or not `--expect-candidate`), and, unless `--allow-uncommitted`, a target or harness that differs from its commit. Take `--expect-run` from the run's own last log line (`RESULTS … run <runId> …`). In this repo the only scripts that read results files are the two self-test scripts (each checks the fields it needs itself; selftest-staging.js also runs the verifier on its control run and shows it rejecting a wrong run id, target sha256, candidate and manifest); reports cite results files: quote the verifier's `VERIFY OK` line with them.

## Release runs and the manifest (audit 5)
`manifest.json` lists every case module (`wallet.test.js`, `audit2.test.js`, `audit3.test.js`, `audit3b.test.js`, `harness.test.js`, every `audit4*.test.js` and `audit5*.test.js`) with its group and the exact ids it must register. With `RELEASE=1` the runner refuses to start (exit 2, results status `manifest-mismatch`) when a listed module is missing, a module or an id is present but not listed, a listed id is not registered, or a group differs; `RELEASE=1` also refuses `CASES` and any preloaded code in `NODE_OPTIONS` (`--require`, `--import`, `--loader`). A missing audit module therefore can never shrink a release run. Adding a module or a case is deliberate: add it to manifest.json in the same commit (`node wallet.test.js --print-manifest` prints the current registration to copy from). Runs without `RELEASE=1` are labelled `subset` (CASES given) or `all (not release-verified)` and print a `WARN` line when the registration differs from the manifest.

## Results file (schema `stormglass-wallet-results/2`, audit 5)
`$OUT/results-$LABEL.json` is one object (it used to be a bare array of case rows: that array is now the `cases` field, same row format plus `file`, the module that registered the case). Readers of the old format: use `j.cases` (or `Array.isArray(j)?j:j.cases`). Fields: `runId` (unique), `label`, `mode` (`release` / `subset` / `all (not release-verified)`), `status` (`starting`, `running`, `passed`, `failed`, `incomplete`, `interrupted`, `harness-failure`, `selection-error`, `registration-error`, `manifest-mismatch`), `completed` (every selected case executed and the run was not cut short), `exit` (the exit status, or `"interrupted"`; `exitCode` always has the number), `startedAt`, `finishedAt`, `interruptedBy`, `running` (the case in progress when it was cut short), `target` (path, bytes, sha256, `source`: `commit` = `git rev-parse HEAD` of the repo holding TARGET, `path` in that repo, `matchesHead` = TARGET's bytes equal the file in that commit, or `commit:"unknown"` and a `reason`), `harness` (commit, tree hash of this folder, uncommitted files, and the sha256 of every file of this folder Node loaded), `deps` (node, playwright and ethers as actually loaded, the ethers UMD sha256, chromium version), `env` (CASES, RELEASE, timeouts, NODE_OPTIONS, OUT, PORT), `manifest` (the comparison with manifest.json), `registered`, `groups`, `selected`, `executed`, `passed`, `failed`, `timedOut`, `unexecuted`, `harnessFailures`, `persistence` (`ok`, `snapshots`, `failures`, `previous`).

Persistence: the file is written atomically (a temp file in the same folder, fsync, rename) before the first case, after every case and at the end. Any failure to write it is a harness failure that makes the exit status nonzero for the rest of the run (a later good write records it, never clears it); if the results cannot be written at the start, no case runs. A file of the same name left by an earlier run is first renamed to `results-$LABEL.prev-<its runId>.json` (`prev-legacy-<mtime>` for the old array format), so an older successful run can never pass for the current one; if the final write fails, the file on disk is the previous snapshot, which says `running`, never `passed`. A dependency, the target or a case module that cannot be loaded still ends with a results file (`harness-failure` / `registration-error`).

Watchdogs: `CASE_TIMEOUT_MS` (default 120000) fails a case that gives no result in time (`timedOut`), closes its contexts and refuses any late `boot()` from it; if the browser then does not answer within 15 s it is killed and the run ends `incomplete`. `RUN_TIMEOUT_MS` (default 2700000) ends the whole run as `interrupted`. SIGTERM / SIGINT (run.sh passes them to node) write an `interrupted` result and exit 143 / 130.
