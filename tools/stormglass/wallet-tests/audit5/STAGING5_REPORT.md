## 4b. The staging boundary, as found in the code (audit 5b, Finding D)
Correction (audit 5b): earlier wording could be read as "staging never contacts the real WalletConnect relay". That is true of SIMULATION only. In REAL WALLET mode the page does contact real providers and, on a phone, the real WalletConnect relay. The automated tests never did, because the test environment blocks every socket and outside host; that is a property of the test environment, not evidence that the deployed page cannot reach a relay.

**SIMULATION** (default): simulated wallets and simulated results, no real provider. `__SG.eth()` returns the simulated window.ethereum or nothing (stage.js `SG.eth`), `__SG.detail()` drops every announcement that is not a simulated wallet (`SG.detail`), `__SG.wcNS()` returns the simulated WalletConnect namespace, so /wc.js never loads and no relay socket opens (`SG.wcNS`, `SIM_WC_NS`). Every cross-origin JSON-RPC POST is answered by the simulated chain (`window.fetch` wrap).

**REAL WALLET**: every provider the page can obtain is a wrapper made in stage.js `wrap()` (memoised per raw provider; exposes request, the event methods, the name flags, providers[] wrapped; for WalletConnect also accounts, a frozen copy of session, a signer facade with only `client.on('session_request_sent')`, enable, disconnect). The acquisition paths (each tapped by build.js and refused by the build if the page reads a provider any other way, st13):
- window.ethereum (11 reads → `__SG.eth()`), its legacy providers[] (wrapped on read);
- EIP-6963 announcements (the one listener → `__SG.detail()`);
- WalletConnect (`_wcGlobal` → `__SG.wcNS()` → `wrapNS`: `EthereumProvider.init` returns `wrap(provider)`);
- a remembered choice (localStorage `stormglass.wallet`, and on phones `SG_WC_APP`) only selects among those wrapped providers; it holds a key, never a provider.

What reaches the real wallet / relay (permitted connection and session operations):
- the liveness and state checks with no prompt: `eth_chainId`, `eth_accounts` (picker ping, opBegin/opCheck);
- `eth_requestAccounts` and `wallet_switchEthereumChain`: only after the visitor presses ASK MY WALLET on the staging gate. Audit 5b: one ASK MY WALLET now lets exactly one request through (a WalletConnect pairing arms the page's following eth_requestAccounts once); before, any eth_requestAccounts of the same wallet within 20 s of an earlier ASK (a reconnect right after DISCONNECT) went to the wallet without the gate (fixed, st33/st35/st36);
- `wallet_revokePermissions` (DISCONNECT);
- read-only calls (`eth_blockNumber`, `eth_call`, `eth_getBlockByNumber`, `eth_getLogs`, `eth_getTransactionReceipt`, `eth_getTransactionByHash` for a hash that is not a simulated one): these reach the wallet's node only when the page reads through the wallet (its fallback after the three HTTP readers fail, which the simulated readers do not do); a simulated hash is answered by staging;
- WalletConnect: `EthereumProvider.init` opens the real relay connection when CONNECT is pressed on a phone, BEFORE the staging gate (no request goes to the phone wallet then; a session this site stored in localStorage is restored, since REAL mode shares the live site's storage), then `enable` = the pairing proposal over the relay only after ASK MY WALLET, the session's own events (account and network changes, deletion), and `disconnect`. WalletConnect's own HTTP hosts are let through the fetch wrap in REAL mode (`WC_HOST`), JSON-RPC writes excepted (`HTTP_WRITE` is refused first).

What is stopped before the wallet and the relay (default-deny at the wrapper's `request`, stage.js `guard`): `eth_sendTransaction` (every contract write) opens the intercept panel and the visitor picks a simulated result; `wallet_sendTransaction`, `wallet_sendCalls`, `eth_sendRawTransaction`, `eth_signTransaction`, `eth_sendUserOperation`, `wallet_grantPermissions`, `eth_sign`, `personal_sign`, `eth_signTypedData*` are shown and refused (4001); every other method, a made-up name included, is refused with 4200. The method name is read once (a name that changes between reads cannot switch a check). Inside the WalletConnect bundle a belt patches the raw provider's request / send / sendAsync, signer.request and the sign client's request to refuse anything matching send or sign (eth_sendUserOperation and wallet_sendCalls included). Audit 5b: a listener added through a wrapper now runs with `this` = the wrapper, never the raw provider (an EventEmitter-style wallet calls listeners with `this` = itself, which would have handed the raw object to page code).

Chain outcomes shown in staging stay simulated: the result of every intercepted transaction, and the sale, owed and payout state, come from the simulated chain in the page.

The automated tests (st1-st42) run with the harness's mock wallets and mock WalletConnect and with every WebSocket and outside host blocked. They prove the wrapper and its gate; they never prove, and are not evidence, that the deployed page cannot reach the relay or that a real relay delivers anything.

## 9. Limitations (what staging cannot prove)
- **Real wallet payment screens and real WalletConnect relay delivery are never exercised.** Payments and signatures stop at the wrapper; the intercept panel says so. withdrawTo is no different: a real wallet's own handling of a withdrawTo request (what it shows for an unnamed address argument, whether it simulates it as safe) is not tested here.
- **The wallet's own errors are modelled by code only.** Scenario 6 makes a simulated wallet answer eth_requestAccounts with a chosen JSON-RPC code, as a rejected promise or a synchronous throw. Real wallets' messages, extra fields (`data`, nested `error`), their behaviour on repeated requests, and an EIP-6963 wallet that throws on announcement are not modelled. The phone is a user-agent override on whatever browser opens the page: iOS Safari's backgrounding, app switching and deep-link return are not exercised (the Navigation-API hold, from audit 4, only shows the link).
- **The identity controls change only what the simulated readers and the simulated wallet answer to eth_getTransactionByHash.** A real reader's other failure modes (stale cache, a reorged block, rate limits, a node that lies consistently across all three readers and the wallet) are not modelled. In REAL mode the page never asks the real wallet about a simulated hash (the staging layer answers it), so how a real wallet answers eth_getTransactionByHash is not tested.
- **The simulated contract is simplified.** It models owed(), withdraw(), withdrawTo(address) (revert when nothing is owed, when the payee rejects ETH, on the zero address) and a flat 0.0364 ETH of pending earnings per account; seat accounting, the 70/20/10 split, the real gas cost and a real contract's receive() behaviour (a smart wallet that spends more than 60,000 gas, as `_pay` limits) are not run. Whether a payee "rejects ETH" is a switch, not a computation. Seat earnings settle on buy/witness only after card 8's SET UP.
- **FAST CLOCK and the receipt controls change what the staging page's tracking sees**, as in audit 4; an audit-5 row ends at the first poll rounds (the pending window is under 20 s).
- **Staging patches the page's provider reads.** The staging page differs from the candidate by the seven patches above (and the runtime); st22 undoes them exactly. A path the build does not tap (a provider obtained some other way) is refused by the build (st13), not silently allowed.
- **Shared origin with the live site.** A REAL-mode WalletConnect session shares the live page's storage, as two tabs of dithervoid.art would. SIMULATION uses its own per-tab copy.
- **The automated runs contacted no real wallet, RPC or relay: that is the test environment.** The harness refuses every page request outside 127.0.0.1 and every WebSocket; the wallets are mocks. This is a property of the test environment only: the deployed staging page in REAL WALLET mode does contact a real wallet and, on a phone, the real WalletConnect relay for the connection (4b). The proxy may report failed connections to mtalk.google.com:5228 from Chromium's own background service; they were refused.
- **Owed changes and the replacement-that-withdrew are simulated (audit 5b).** CHANGE NOW / ARM change the simulated owed[] only; the replacement is a simulated withdraw(); the real contract's behaviour (pay all owed at execution, revert "nothing owed") is modelled, not run.
- The staging page's own wording (cards, intercept rows) was written for the owner and the reviewers; it is not shipped to visitors.
